# Кубышка — архитектура

## 1. Форма системы

Приложение — локальная база данных в браузере с фоновой репликацией на собственный сервер. Это не «клиент к API»: интерфейс никогда не ждёт сеть, он читает и пишет IndexedDB, а сервер нужен только чтобы два телефона видели одни и те же данные.

```
iPhone (PWA)                              VPS (docker compose)
┌──────────────────────────────┐          ┌──────────────────────────┐
│ UI (React)                   │          │ Caddy ── TLS, статика    │
│   ↕ читает/пишет мгновенно   │          │   ↓                      │
│ Dexie / IndexedDB  ← истина  │          │ Fastify ── /auth /sync   │
│ ключ семьи только здесь      │          │ шифротекст, без ключа    │
│   ↕ очередь изменений        │  HTTPS   │   ↓                      │
│ Sync engine ─────────────────┼─────────▶│ PostgreSQL               │
│ Service worker ── оболочка   │          │ pg_dump по расписанию    │
└──────────────────────────────┘          └──────────────────────────┘
```

Следствие для сроков: сервер содержит два эндпоинта синхронизации и аутентификацию, вся продуктовая логика живёт на клиенте. Это примерно 400 строк серверного кода вместо полноценного REST на каждую сущность.

## 2. Стек

| Слой | Выбор | Почему именно он |
| --- | --- | --- |
| Клиент | React 19, TypeScript, Vite | Скорость разработки, предсказуемость |
| Локальная БД | Dexie 4 + `useLiveQuery` | IndexedDB без ручной работы, реактивные запросы без слоя состояния |
| Состояние | Только Dexie и локальный `useState` | Redux и TanStack Query не нужны: источник истины один и он локальный |
| Стили | Tailwind CSS 4 с токенами тем | Нет отдельных файлов стилей, тёмная тема переменными |
| Компоненты | Свои | Готовые библиотеки не дают ощущение iOS и весят больше, чем требование N-6 |
| Графики | Свои SVG-компоненты | Нужны три вида графиков; любая библиотека съедает весь бюджет размера |
| PWA | `vite-plugin-pwa` (Workbox) | Манифест, service worker и обновление без ручного кода |
| Сервер | Node 24, Fastify 5, TypeScript без сборки | Node исполняет TypeScript напрямую, шаг компиляции не нужен |
| БД-слой | Drizzle ORM, миграции обычным SQL | Типы из схемы; генератор миграций не нужен при редких изменениях |
| Валидация | Zod, схемы в общем пакете | Одни и те же правила на клиенте и сервере |
| Инфраструктура | docker compose, Caddy | Автоматический Let's Encrypt, один файл конфигурации |
| Пакеты | npm workspaces | Отдельный менеджер пакетов ради трёх пакетов не нужен |

Рассмотрен и отклонён PocketBase: дал бы готовую аутентификацию и репликацию, но навязывает свою модель сессий, которая не ложится на вход по PIN без почты, и не оставляет места для оффлайн-слияния по нашим правилам.

```
│   │       ├── db/             схема Dexie, миграции, репозитории
│   │       ├── sync/           очередь, цикл синхронизации, разрешение конфликтов
│   │       └── ui/             кнопки, листы, клавиатура, графики
│   └── api/

│           ├── routes/         auth.ts, sync.ts, family.ts
│           ├── db/             схема Drizzle, миграции
│           └── lib/            токены, хеширование PIN, коды приглашений

```

`packages/shared` — единственное место, где описаны сущности. Клиент и сервер импортируют оттуда типы и схемы; добавление поля правится в одном файле.

## 4. Модель данных

Все суммы — целое число копеек (`bigint`). Все идентификаторы — UUID v7, генерируются на клиенте: операция существует до того, как сервер о ней узнал, и не меняет идентичность после синхронизации.

### 4.1. Общие поля реплицируемых таблиц

| Поле | Назначение |
| --- | --- |
| `id` | UUID v7 с клиента |
| `family_id` | Граница видимости, единственный ключ изоляции |
| `updated_at` | Время правки на клиенте, основа разрешения конфликтов |
| `seq` | `bigint` из общей последовательности, присваивается сервером при записи, курсор для выборки изменений |
| `deleted` | Мягкое удаление |
| `updated_by` | Участник, сделавший правку |

### 4.2. Сущности

```
family        id, name, savings_norm, expected_income, created_at
member        id, family_id, name, pin_hash, avatar_color, created_at
device        id, member_id, label, refresh_token_hash, webauthn_credential, last_seen_at
invite        id, family_id, code_hash, expires_at, used_at, created_by

account       id, family_id, name, kind, scope, owner_member_id, opening_balance,
              credit_limit, icon, color, sort, archived
category      id, family_id, name, flow, icon, color, sort, archived
transaction   id, family_id, flow, amount, account_id, counter_account_id, category_id,
              member_id, occurred_at, note, tags, created_by
budget        id, family_id, category_id, period_month, amount
```

- `account.kind` — наличные, дебетовая карта, кредитная карта, накопительный счёт. `scope` — общий или личный.
- `transaction.flow` — расход, доход, перевод. У перевода заполнен `counter_account_id` и пуст `category_id`.
- `budget.period_month` — первое число месяца, один лимит на пару «категория и месяц».
- `family.savings_norm` — сколько семья намерена откладывать в месяц; хранится на уровне семьи, потому что бюджет общий.
- `family.expected_income` — ожидаемый доход в месяц. Без него прогноз накоплений до прихода зарплаты был бы отрицательным и бесполезным.

На сервере у этих таблиц остаются только поля из раздела 4.1 и `ciphertext`. Перечисленные содержательные колонки живут в локальной базе и внутри шифротекста. Уникальный индекс лимита «категория и месяц» сервер больше не держит: пара спрятана в шифротексте. Экран лимитов правит уже существующую строку.

### 4.3. Что не хранится

Отложенное за месяц — не сущность, а вычисление: доходы месяца минус расходы месяца. Переводы в копилку в него не входят, иначе деньги считались бы дважды. Прогноз на конец месяца берёт ожидаемый доход (или фактический, если тот уже больше) и вычитает расходы, экстраполированные по текущему темпу. Обе функции живут в `packages/shared` и не зависят ни от сети, ни от хранилища.

Баланс счёта и суммы по категориям не хранятся нигде. Они вычисляются из операций на клиенте при загрузке: при объёме до нескольких тысяч записей это единицы миллисекунд, а любое хранимое агрегированное значение пришлось бы чинить после каждой офлайн-правки.

## 5. Синхронизация

### 5.1. Запись

1. Пользователь сохраняет операцию, Dexie пишет запись и добавляет её `id` в таблицу `outbox` в одной транзакции.
2. UI обновляется подпиской `useLiveQuery` — ещё до того, как начнётся отправка.
3. Планировщик синхронизации срабатывает по любому из событий: запуск, возврат приложения на экран, появление сети, изменение `outbox` с задержкой в 2 секунды.

### 5.2. Обмен

```
POST /sync
  → { cursor, changes: { transactions: [{ id, familyId, updatedAt, updatedBy, deleted, ciphertext }] } }
  ← { cursor, serverTime, changes: { transactions: [{ ...те же поля, seq, ciphertext, legacy }] } }
```

Один эндпоинт делает обе стороны обмена, поэтому состояние всегда согласовано после одного запроса. Сервер в одной транзакции применяет присланные конверты, присваивает им новые `seq` и отдаёт всё, что изменилось с курсора клиента, включая только что принятое. Содержимое конверта сервер не читает: конфликт по-прежнему решается сравнением `updated_at` у записи целиком, и при победе заменяется весь `ciphertext`.

`legacy` — временное поле миграции. Пока клиент не перезалил старую открытую строку, там лежит JSON прежних колонок. Как только приходит шифротекст той же или более новой версии, сервер стирает `legacy`. Новые семьи этого поля не заполняют.

### 5.3. Конфликты

Побеждает запись с большим `updated_at`, при равенстве — с большим `id`. Правило применяется к записи целиком, а не по полям: для двух человек с общим бюджетом вероятность одновременной правки одной операции мала, а пофайловое слияние стоило бы нескольких дней работы.

Удаление — обычная правка с `deleted = true`, поэтому не воскрешает запись при расхождении часов.

### 5.4. Часы

Клиентские часы могут врать. При каждом ответе сервер присылает своё время, клиент хранит смещение и подставляет скорректированное время в `updated_at`. Это убирает основную причину неверных слияний.

## 6. Доступ

### 6.1. Первый вход

Запрос создания семьи принимается только пока в базе нет ни одной семьи. После создания эндпоинт отвечает отказом навсегда. Окно уязвимости — промежуток между развёртыванием и первым открытием приложения; его можно закрыть переменной `SETUP_CODE` в `.env`, если сервер смотрит в интернет заметное время до первого входа.

### 6.2. Приглашение

Участник запрашивает код, сервер хранит его хеш с временем жизни 24 часа. Второй человек вводит код, своё имя и свой PIN, получает собственного `member` и устройство. Код сгорает. Код не защищает записи: вместе с ним второе устройство получает ключ семьи. Ключ стоит во фрагменте ссылки после `#` и на картинке QR. Браузер не отправляет фрагмент на сервер. Шести цифр без ключа недостаточно, чтобы прочитать данные.

### 6.3. Сессии

Устройство получает непрозрачный токен, который хранится в cookie `HttpOnly`, `Secure`, `SameSite=Lax` на год. На сервере лежит только его хеш, поэтому отзыв устройства — это удаление строки. JWT не используется: подпись ничего не добавляет при двух пользователях, зато усложняет отзыв.

Cookie выставляется сервером: ограничение Safari на семь дней касается хранилищ, созданных скриптом, и серверную cookie не затрагивает. Дополнительно при первом входе запрашивается `navigator.storage.persist()`, чтобы iOS не вытеснила локальную базу.

### 6.4. Блокировка приложения

PIN проверяется локально: в IndexedDB лежит PBKDF2-хеш со случайной солью, поэтому разблокировка работает офлайн. На сервере PIN хешируется scrypt из стандартной библиотеки Node, без нативных зависимостей. Face ID подключается как платформенный ключ WebAuthn поверх того же локального состояния. Запрос блокировки — не чаще раза в сутки с момента последней успешной разблокировки.

PIN защищает от человека, взявшего разблокированный телефон, и не является защитой данных на сервере. Записи на сервере защищает ключ семьи, которого у сервера нет.

### 6.5. Шифрование семьи

Ключ семьи — случайные 32 байта AES-256-GCM. Его создаёт телефон, на котором заводят семью, через WebCrypto. Рядом создаётся ключ восстановления: те же права, другая упаковка. Ключ восстановления оборачивает семейный ключ алгоритмом AES-KW. На сервер уходит только обёрнутый ключ, в таблицу `family_keys`. Открытый ключ туда не попадает.

На устройстве в IndexedDB лежат две вещи. Неэкспортируемый `CryptoKey` используется для шифрования и не отдаётся через `exportKey`. Строка ключа восстановления хранится рядом, чтобы хозяин мог снова её увидеть в «Ещё» после PIN или Face ID. Без этой строки показать ключ позже нельзя: неэкспортируемый ключ из хранилища не извлекается.

Каждая синхронизируемая запись шифруется отдельно. В дополнительные данные AES-GCM входят таблица, `id`, `family_id` и `updated_at`, поэтому шифротекст нельзя переставить между записями. Внутри JSON — все содержательные поля: суммы, названия, заметки, лимиты, иконки, нормы. Локальная база по-прежнему хранит их открыто, иначе интерфейс не смог бы читать IndexedDB без сети.

Счета и категории при создании семьи записывает клиент и сразу отправляет уже зашифрованными. Сервер больше не сеет их сам.

Ключ восстановления показывают один раз после создания семьи и просят сохранить его в менеджере паролей или на бумаге. Новый телефон входит по коду приглашения или по имени и PIN, а записи открывает этим ключом: скачивает обёртку и разворачивает её локально. Если не осталось ни одного устройства и ключ восстановления потерян, прочитать записи нельзя. Дамп Postgres этого не меняет: в нём тот же шифротекст.

Что сервер по-прежнему видит открытым текстом:

| Данные | Зачем они открыты |
| --- | --- |
| `id`, `family_id`, `updated_at`, `updated_by`, `deleted`, `seq` | Синхронизация и выбор победившей версии |
| `ciphertext`, а до перезаливки ещё `legacy` | Само зашифрованное содержимое и мост со старой схемы |
| Имя участника, хеш PIN, цвет, подпись устройства | Вход по имени и PIN и список участников. Это не финансовые поля |
| Хеш кода приглашения, хеш токена устройства | Проверка доступа. Самих секретов в базе нет |
| `wrapped_key` | Обёртка AES-KW. Без ключа восстановления из неё не получить семейный ключ |

Имена счетов, категорий, заметки, суммы, лимиты, норма и ожидаемый доход в эту таблицу не входят: они внутри `ciphertext`.

## 7. Подсказка категории

Индекс строится один раз при запуске из последних 500 операций и обновляется инкрементально после каждого сохранения.

Оценка каждой категории — взвешенная сумма нормированных признаков:

| Признак | Смысл |
| --- | --- |
| Частота за 90 дней | Базовая вероятность |
| Давность последнего использования | Недавние категории вероятнее |
| Близость суммы к типичной для категории | Разделяет кофе за 300 ₽ и продукты за 4000 ₽ |
| Совпадение времени суток | Обед, вечерние покупки |
| Совпадение дня недели | Выходные траты |

Показываются шесть лучших. Веса — константы в одном модуле, подбираются на реальных данных через неделю использования. Выбор через «Другое» попадает в индекс и поднимает категорию в следующий раз.

Алгоритм — чистая функция от истории и контекста, без состояния и без сети: тестируется без браузера и выполняется за доли миллисекунды.

## 8. Рекомендации

Каждое правило — функция `(снимок данных) => рекомендация | null`. Правила перечислены в одном массиве, движок применяет все и сортирует результат по весу значимости. Добавление правила не затрагивает существующие.

Правила первой версии: темп расходования лимита, аномальный рост категории относительно медианы трёх месяцев, прогноз накоплений на конец месяца относительно нормы, нетипично крупная трата.

Рекомендации пересчитываются при изменении данных и не хранятся; скрытые пользователем помечаются в локальной таблице до конца месяца.

## 9. Развёртывание

```
docker compose up -d     # caddy, api, postgres
```

- Caddy завершает TLS, отдаёт собранную статику и проксирует `/api` на Fastify. Если на сервере уже есть обратный прокси, Caddy из набора исключается, а приложение публикуется на внутреннем порту.
- Миграции накатываются при старте контейнера API.
- Резервная копия: `pg_dump` по расписанию в каталог на хосте, 14 копий, восстановление одной командой.
- Обновление: `git pull && docker compose up -d --build`.
- Клиентская часть версионируется. Service worker предлагает обновиться только после сверки с опубликованным `integrity.json`: клиент качает манифест с `https://raw.githubusercontent.com` и сверяет SHA-256 файлов новой сборки. Несовпадение или недоступность манифеста оставляет старую версию.
- Caddy отдаёт жёсткий Content-Security-Policy: скрипты и воркеры только со своего origin, сеть только к своему API и к `raw.githubusercontent.com` для этой сверки, без inline-скриптов и `eval`. Стили компонентов остаются атрибутами, потому что интерфейс собран на них.

## 10. План итераций

| Итерация | Дни | Результат, который можно открыть на телефоне |
| --- | --- | --- |
| 1. Каркас | 1–3 | Приложение развёрнуто на домене, ставится на домашний экран, создаётся семья, вход по PIN, пустые экраны |
| 2. Ядро | 4–7 | Счета, категории, быстрый ввод с подсказками, список операций, работающая синхронизация между двумя телефонами |
| 3. Контроль | 8–10 | Лимиты по категориям, карточка месяца с накоплениями и прогнозом, экран накоплений, аналитика за месяц |
| 4. Смысл | 11–14 | Рекомендации, приглашение второго участника, Face ID, тёмная тема, тактильный отклик, полировка |

После второй итерации приложением уже можно пользоваться ежедневно: всё остальное добавляется поверх накопленных данных.

## 11. Принятые ограничения

1. Двое пользователей и один сервер — отказ от очередей, кеширующего слоя и горизонтального масштабирования.
2. Последняя запись побеждает — отказ от CRDT и истории версий полей.
3. Агрегаты считаются на клиенте — отказ от материализованных представлений и серверной аналитики.
4. Нет почты и внешних входов. Сессию можно вернуть со второго устройства или по имени и PIN. Прочитать записи без ключа восстановления нельзя, в том числе из консоли сервера и из ночного дампа.
5. Нет CI и staging — качество держится на типах, схемах Zod и тестах доменных функций.
