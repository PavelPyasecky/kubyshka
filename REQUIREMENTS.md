# Кубышка — требования

PWA для семейного бюджета. Основная платформа — iPhone (Safari, установка на домашний экран). Пользователи: 2 взрослых, равные права, общий бюджет.

Источник: ответы на `REQUIREMENTS-QUESTIONS.md`. Незаданные явно пункты приняты по рекомендуемым значениям.

## 1. Продуктовые принципы

1. **Ввод операции — главный сценарий.** Два действия: ввести сумму, тапнуть категорию. Всё остальное подставляется и правится потом.
2. **Приложение всегда отзывчиво.** UI читает и пишет только локальную базу; сеть — фоновый процесс, её отсутствие не блокирует ничего, кроме приглашения второго участника.
3. **Общий бюджет по умолчанию.** Оба видят всё, авторство операции фиксируется, но не ограничивает.
4. **Ничего лишнего в v1.** Цели, экспорт, подписки, фото чеков отложены, но модель данных их не исключает.

## 2. Функциональные требования

### 2.1. Доступ

| ID | Требование |
| --- | --- |
| A-1 | Первое открытие на пустой базе: ввод имени и PIN из 4 цифр создаёт семью и первого участника |
| A-2 | После создания семьи регистрация закрывается: войти можно только по коду приглашения |
| A-3 | Участник генерирует код из 6 цифр, действующий 24 часа и сгорающий после первого использования |
| A-4 | Устройство входит один раз и остаётся авторизованным; сессия не истекает по времени |
| A-5 | Открытие приложения требует PIN, но не чаще раза в сутки на устройство |
| A-6 | PIN можно заменить на Face ID через WebAuthn; PIN остаётся запасным способом |
| A-7 | Разблокировка работает офлайн |
| A-8 | Участник видит список устройств семьи и может отозвать любое |

### 2.2. Счета

| ID | Требование |
| --- | --- |
| S-1 | Типы: наличные, дебетовая карта, кредитная карта, накопительный счёт |
| S-2 | Счёт общий (видят и пополняют оба) или личный (видит только владелец, но суммы входят в общий расход семьи) |
| S-3 | Счёт имеет название, иконку, цвет, начальный остаток |
| S-4 | Баланс вычисляется как начальный остаток плюс операции; вручную не редактируется |
| S-5 | Счёт архивируется, но не удаляется, если по нему есть операции |
| S-6 | Для кредитной карты хранится лимит, показывается доступный остаток и задолженность |

### 2.3. Операции

| ID | Требование |
| --- | --- |
| O-1 | Типы: расход, доход, перевод между счетами |
| O-2 | Перевод не влияет на суммы доходов и расходов |
| O-3 | Экран ввода: цифровая клавиатура и лента из 6 предсказанных категорий; тап по категории сохраняет операцию |
| O-4 | По умолчанию подставляются: последний использованный счёт, текущая дата, текущий участник |
| O-5 | Кнопка «Другое» открывает полный список категорий с поиском |
| O-6 | После сохранения 5 секунд доступна отмена, затем правка через карточку операции |
| O-7 | Операция содержит необязательные заметку и теги |
| O-8 | Удаление мягкое, с сохранением автора и времени изменения |
| O-9 | Список операций сгруппирован по дням, с итогом за день, поиском и фильтрами по счёту, категории, участнику, периоду |

### 2.4. Подсказка категории

| ID | Требование |
| --- | --- |
| P-1 | Подсказка вычисляется на устройстве по локальной истории, без обращения к серверу |
| P-2 | Учитываются: частота за 90 дней, давность, близость суммы, время суток, день недели |
| P-3 | Выбор пользователя, в том числе через «Другое», влияет на следующие подсказки |
| P-4 | До накопления истории показываются предустановленные частые категории |
| P-5 | Расчёт подсказок не превышает 16 мс при 2000 операций в локальной базе |

### 2.5. Категории и лимиты

| ID | Требование |
| --- | --- |
| C-1 | Предустановленный набор из 20 категорий расходов и 5 категорий доходов, с иконками |
| C-2 | Категории создаются, переименовываются и архивируются; уровень один |
| C-3 | Лимит задаётся на категорию на календарный месяц |
| C-4 | Лимит по умолчанию переносится на следующий месяц |
| C-5 | Показывается потрачено, остаток, доля месяца и предупреждение, если темп трат опережает календарь |
| C-6 | Превышение лимита отображается явно, но не блокирует ввод |

### 2.6. Накопления

| ID | Требование |
| --- | --- |
| K-1 | Отложено за месяц = доходы месяца минус расходы месяца; переводы между счетами на это значение не влияют |
| K-2 | Значение считается само, от пользователя не требуется никаких действий сверх ввода операций |
| K-3 | Норма накопления — сумма в месяц, задаётся один раз и действует до изменения |
| K-4 | Ожидаемый доход в месяц задаётся один раз и действует до изменения |
| K-5 | Прогноз на конец месяца = ожидаемый доход минус расходы, экстраполированные по текущему темпу |
| K-6 | Если фактический доход месяца превысил ожидаемый, в прогнозе используется фактический |
| K-7 | Прогноз сравнивается с нормой: выполнение показывается в процентах и цветом |
| K-8 | На главном экране «Потрачено» и «Отложено» — одна карточка в две колонки, под ними строка прогноза |
| K-9 | Тап по колонке «Отложено» открывает экран накоплений |
| K-10 | Копилка одна: сумма счетов с типом «накопительный счёт» |
| K-11 | Показывается разрыв между отложенным и фактически переведённым в копилку |
| K-12 | Перевод в копилку создаётся с экрана накоплений одной кнопкой, с подставленной суммой разрыва |
| K-13 | История помесячных накоплений за 12 месяцев с линией нормы; текущий месяц показан как прогноз |
| K-14 | Средние накопления за три месяца сравниваются с нормой |
| K-15 | Месяц с отрицательным результатом отображается явно, как перерасход, а не как ноль |

### 2.8. Рекомендации

| ID | Требование |
| --- | --- |
| I-1 | Рекомендации — детерминированные правила, считаются на устройстве, объяснимы и воспроизводимы |
| I-2 | Правило «темп трат»: лимит категории будет превышен при сохранении текущей скорости |
| I-3 | Правило «аномалия»: расход по категории заметно выше медианы трёх предыдущих месяцев |
| I-4 | Правило «прогноз накоплений»: сколько отложится к концу месяца и хватает ли этого до нормы |
| I-5 | Правило «крупная трата»: операция существенно выше обычной для своей категории |
| I-6 | На главном экране не более трёх рекомендаций, отсортированных по значимости |
| I-7 | Рекомендацию можно скрыть, она не возвращается в этом месяце |
| I-8 | Набор правил расширяется добавлением одной функции, без изменения существующих |

## 3. Нефункциональные требования

| ID | Требование |

| N-2 | Сохранение операции в локальную базу — менее 50 мс, без ожидания сети |

## 5. Вне первой версии

Цели с датой и расчётом «успеваете ли», несколько копилок, экспорт в CSV и XLSX, импорт выписок, повторяющиеся платежи, фото чеков, push-уведомления, деление операции на несколько категорий, учёт долгов между участниками, роли для детей, мультивалютность.

Модель данных и структура модулей проектируются так, чтобы каждый пункт добавлялся без переписывания существующего.

## 6. Открытые вопросы

1. Параметры VPS: провайдер, ОС, оперативная память, что уже занимает 80 и 443 порт.
2. Домен или поддомен для приложения.
3. Нужно ли встраиваться в существующий обратный прокси или поднимать свой.
